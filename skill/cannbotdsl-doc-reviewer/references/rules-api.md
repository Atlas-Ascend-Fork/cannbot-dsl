# API 文档写作规范

适用范围：`docs/zh/api/` 下所有文档，分三类：

- **接口文档**：描述单个接口的文档，一级标题为接口名，套用本文件 API 规则
- **类/数据结构文档**：类/枚举/结构定义页，一级标题为类名，套用 DS 规则
- **概览页**：接口与类定义之外的导航与专题页（分类导览、特性说明、概念综述等），不套用本文件骨架规则，按维度 1 检查（目录索引登记 API-28 仍适用）

规则来源与优先级：本文件以仓库内 `docs/zh/api/api-template.md`（检查时读取）为基础制定，并可在模板要求之上更严格；**检查以本文件规则为准**，本文件未覆盖的方面以模板为底线。存量文档按本文件规则逐步整改，存量写法不作为合规依据。

规则编号范围：接口文档 `API-01~28`，类/数据结构文档 `DS-01~04`。

本文件分两部分：**规则**（按文档章节组织，写作时遵守）与**检查方法**（排查验证手段）。

## 规则

### 章节结构（API-01~04）

接口文档固定 7 个二级章节，顺序不可颠倒、不得改名：

```
# <接口名>
## 产品支持情况
## 功能说明
## 函数原型
## 参数说明
## 返回值说明
## 约束说明
## 调用示例
```

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-01 | 接口文档 7 个章节齐全且顺序固定，不得删减章节或改名（"约束说明"不可写成"使用约束"、"参数说明"不可写成"参数"）；可适当扩展新增章节（如"使用建议"），但不得破坏既有章节顺序 | HIGH |
| API-02 | "产品支持情况"必须是第一个二级标题（接口文档与类文档通用） | HIGH |
| API-03 | 一级标题：接口文档为接口名（可带 `(...)` 表示带参形式），类文档为类名，均**不用反引号包裹**；标题须与函数原型中的接口名/代码中的类定义名一致 | HIGH |
| API-04 | 当接口无参数/无返回值/无约束等导致对应章节（如"参数说明"）无实际内容时，**章节节点必须保留**：标题不得省略或删除，正文内容写"无" | HIGH |

### 产品支持情况（API-05~06）

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-05 | 产品名称严格与模板一致（当前为 `Ascend 950PR&950DT系列产品`）；CANNBot-DSL 从 Ascend 950PR&950DT 系列产品开始支持，历史产品型号不写（在文档开头统一声明一次即可）；后续支持新产品后按从新到旧顺序维护，各文档排列顺序保持统一 | HIGH |
| API-06 | 支持状态只写"支持"或"不支持"，不得留空、无中间选项；未经验证的产品不得标记为"支持" | HIGH |

### 功能说明（API-07~11）

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-07 | 介绍接口使用场景和接口功能，通常控制在一至三句话 | HIGH |
| API-08 | 强调"做什么"而非"怎么做"：描述接口提供的能力与效果，不写编译流程和内部调用关系（特殊情况除外，如确需说明机制才能正确使用的接口） | HIGH |
| API-09 | 数学接口应使用公式明确说明覆盖、累加、广播或转置等行为（公式用 `$$...$$` 块，变量下标用 LaTeX 语法）；公式中的变量名须与函数原型中的变量名一致 | HIGH |
| API-10 | 与其他 API 配合使用时，须描述配合关系；与其他 API 功能类似时，须描述两者区别（功能差异、适用场景差异），帮助用户选型 | MEDIUM |
| API-11 | 昇腾领域术语写法参考[昇腾术语表](https://www.hiascend.com/document/detail/zh/Glossary/gls/gls_0001.html)；引入领域新概念时须给出必要解释，并登记 CANNBot-DSL 术语表（`docs/zh/guide/glossary.md`） | MEDIUM |

### 函数原型（API-12~14）

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-12 | 使用三个反引号，并声明语言类型为`python`；统一**不加 `def` 关键字和末尾冒号**，直接写 `函数名(参数) -> 返回类型`（如 `api_name(required_arg: PublicType, optional_arg: PublicType | None = None) -> ReturnType`）；类型使用开发者可见的 Python 或 DSL 类型，不使用内部中间表示类型 | HIGH |
| API-13 | 原型必须与代码实现一致：参数顺序、关键字参数、类型、默认值和返回类型。若 PR 修改了接口签名，对应文档必须同步更新，不得遗留旧原型 | CRITICAL |
| API-14 | 存在多个重载/变体接口时，须分别列出原型并明确标注适用场景 | MEDIUM |

### 参数说明（API-15~20）

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-15 | 固定使用三列表格：`参数`、`输入/输出`、`说明`；每个参数一行，与原型参数一一对应，不得遗漏或多余 | HIGH |
| API-16 | 输入/输出列只使用"输入""输出"或"输入/输出"；特定模式下会读取原值时，明确写出触发条件 | MEDIUM |
| API-17 | "说明"列准确描述参数功能，包括但不限于参数含义/单位/取值范围/默认值/约束信息/可选必选信息；如不涉及，可删减对应内容 | HIGH |
| API-18 | 数值类参数须明确：单位、取值范围、默认值、支持的数据类型；若函数原型中已比较明确（如类型标注完整的数值参数），可不强制 | MEDIUM |
| API-19 | 可选/必选信息：从函数原型看不出来的，须在说明中明确；看得出来的可写可不写，全文保持统一 | MEDIUM |
| API-20 | 数据结构类参数（枚举/类/结构体，如 Tiler、Coord、Channel）：其定义与成员含义须**单独维护一份数据结构类文档**（写法见 DS-01~03）；参数说明中**不得重复罗列数据结构的成员定义**，只须描述参数用途，并附链接指向对应数据结构文档——避免同一数据结构被多个 API 使用时产生多个描述源头 | HIGH |

### 返回值说明（API-21）

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-21 | 明确返回内容和公开类型；通过输出参数返回结果时，说明结果写入哪个参数；存在累加或原地更新时，说明原有数据如何变化。无返回值接口写"无返回值"，并说明结果写入哪个参数 | HIGH |

### 约束说明（API-22~24）

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-22 | 只记录影响接口正确使用的限制，每条约束明确**约束对象、触发条件和具体要求**；不使用"仅适用于支持该能力的场景""需要相应配置"等含糊表述；多个参数存在组合限制时，明确列出合法或非法组合；存在数据依赖时，明确说明发生冲突的访问以及所需的 Channel 或同步关系 | HIGH |
| API-23 | 内容定位：体现该接口的**接口级使用约束**或**较通用的约束**；参数级约束应尽量在参数说明中就近体现，参数组合限制在参数说明难以表述清楚时可在此统一说明；不重复功能说明和参数说明已表达的内容 | MEDIUM |
| API-24 | 约束数量控制：约束过多会影响用户体验，新增约束前应先评估软件是否有优化空间，避免引入不合理的约束 | MEDIUM |

### 调用示例（API-25~27）

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-25 | 首先用一句话说明完整示例实现的功能，随后直接编写 Python 代码块；示例须可独立执行，包含必要的导入、Kernel 定义、Host 调用、设备同步、结果校验和 `main` 入口 | HIGH |
| API-26 | 示例为普通脚本形式，不使用交互式会话格式（`>>>` REPL 风格）；代码块使用三反引号围栏并声明语言类型（python、text 等），上下空一行 | MEDIUM |
| API-27 | 展示预期结果（使用三个反引号，并声明语言类型为`text`，模板标注为"预期结果"）：只展示程序稳定输出；物理核编号等运行时动态值使用占位符，不填写固定数值 | MEDIUM |

### 目录文件维护（API-28）

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| API-28 | API 文档在 `docs/zh/api/` 下维护，目录索引文档为 `docs/zh/api/README.md`；该目录下任何层级的 `.md` 文件新增/删除/移动/重命名时，须同步更新 `README.md` 索引，条目为带相对路径的 `.md` 文件。漏登记或漏同步会导致文档无法从索引到达或产生死链 | CRITICAL |

### 类/数据结构文档（DS-01~04）

固定包含以下部分，顺序不可颠倒：

```
# <类名>
## 产品支持情况
## 简介
## 定义
```

| 编号 | 规则 | 严重级别 |
|------|------|---------|
| DS-01 | 固定包含：类名（一级标题，与代码中类/枚举定义名一致，不用反引号包裹）、产品支持情况、简介、定义，固定部分不得删减、顺序不得改变 | HIGH |
| DS-02 | 简介须回答三点：该类/数据结构**是什么**（表示/描述的对象）、**用来做什么**（典型使用场景）、**关键语义**（核心属性或行为的确切含义，如取值代表什么、如何计数等）；通常一至三句话，不写内部实现与编译细节 | HIGH |
| DS-03 | 定义章节中**每个枚举项/取值必须给出含义说明**：含义简单的，以注释形式在函数原型中直接写清楚（原型写法遵循 API-12）；含义复杂的，以参数说明表格逐项列出（表格格式遵循 API-15） | HIGH |
| DS-04 | 可按需扩展其他子章节（如约束、数据类型使用范围、使用示例、使用建议），但固定部分顺序不得改变；构造函数参数复杂时，可增加参数说明子章节，用表格解释各参数（表格格式遵循 API-15） | MEDIUM |

> 类文档的产品支持情况（API-05~06）要求与接口文档一致。

> 全文通用的表达约定（标识符引用风格、锚点与链接规范、用词等）与术语写法遵循开源写作规范（维度 1）；领域新概念的引入与登记见 API-11。

## 检查方法

### 骨架与章节名检查（API-01、API-02、API-04）

```bash
# 提取二级标题，逐一核对为固定章节名且顺序一致
grep -E '^## ' <目标文件>
# 接口文档固定顺序：产品支持情况 → 功能说明 → 函数原型 → 参数说明 → 返回值说明 → 约束说明 → 调用示例
# 章节名变体（如"使用约束"、二级标题"预期输出"）与缺章均算违规；无实际内容的章节正文应写"无"
```

### 产品支持情况检查（API-05、API-06）

```bash
# 提取"产品支持情况"章节的型号行
awk '/^## /{f=($0=="## 产品支持情况")} f' <目标文件> | grep '^- '
# 产品名与模板一致（当前仅 Ascend 950PR&950DT系列产品，历史型号不写）；状态仅"支持"/"不支持"
```

### 原型格式检查（API-12）

```bash
# 函数原型章节的 python 块内不得出现 def 与末尾冒号（调用示例代码块中的 def 为合法用法）
awk '/^## /{f=($0=="## 函数原型")} f' <目标文件> | grep -n 'def \|: \.\.\.'
```

### 参数表检查（API-15、API-16）

```bash
# 表头应为固定三列：参数 | 输入/输出 | 说明
grep -m1 '^| *参数' <目标文件>
```

### 原型与代码一致性核对（API-13）

接口实现位于 cannbotdsl 包中（本仓不含 DSL 源码）。在可导入 cannbotdsl 的环境中定位包源码后，逐字段比对参数顺序、关键字参数、类型、默认值与返回类型：

```bash
pkg_dir=$(python3 -c "import cannbotdsl, os; print(os.path.dirname(cannbotdsl.__file__))")
grep -rn "def <接口名>" "$pkg_dir" | head
```

包不可导入时，该项标记为"需人工核对"，不得凭文档自身推断放行。

### 说明内容与代码核对（API-13、API-17~19）

参数说明、约束说明中的事实性内容（数据类型列表、取值范围、默认值、对齐要求等）须与 cannbotdsl 包实现一致：在包源码中定位接口与类型定义后比对，漏写、多写均算不一致（数据类型漏写为 HIGH——会让用户误认为不支持）；无法定位实现时标记人工核对。

### README 索引登记检查（API-28）

```bash
cd docs/zh/api
# 目录下实际 .md 文件（排除索引自身）
find . -name '*.md' ! -path './README.md' | sed 's|^\./||;s/\.md$//' | sort > /tmp/files.txt
# 索引中登记的条目（条目须为带相对路径的 .md 链接）
grep -oE '\]\([^)]+\.md\)' README.md | sed 's/^\](//;s/)$//;s|^\./||;s/\.md$//' | sort -u > /tmp/index.txt
comm -23 /tmp/files.txt /tmp/index.txt   # 输出即漏登记文件
comm -13 /tmp/files.txt /tmp/index.txt   # 反向：索引中不存在对应文件的条目（死链）
# 非相对路径条目（绝对链接等，不符合条目格式要求）
grep -nE '\]\([a-zA-Z][a-zA-Z0-9+.-]*://' README.md
```

注意：条目路径相对 `docs/zh/api/README.md` 所在目录，须与文件相对路径完全一致（含子目录层级）。

### 文档站构建校验（收尾，可选）

```bash
cd docs && npm install && npm run build
```

构建失败（死链、索引缺失等）按 CRITICAL 处理；构建告警按对应规则定级。
